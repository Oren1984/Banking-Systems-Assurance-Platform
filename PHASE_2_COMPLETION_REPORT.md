# Phase 2 Completion Report — Banking Source Ingestion and Read-Only Scanning Engine

**Status:** Phase 2 complete. Phase 3 has **not** started. Waiting for explicit approval
before any Phase 3 work begins.

This report is the authoritative record of what Phase 2 actually delivered. Where this
document and `BANKING_PLATFORM_INTEGRATION_PLAN.md` disagree on what is implemented, trust
this document.

---

## 1. Executive summary

Phase 2 transformed the Phase 1 infrastructure foundation into a working local read-only
ingestion and scanning engine. A local directory or ZIP archive can now be safely ingested,
its files discovered and classified under configurable safety limits, mapped to the 16
approved banking domains, scanned by 8 deterministic rule-based scanners, persisted to
PostgreSQL, viewed and filtered through a minimal Streamlit UI, and exported as
JSON/Markdown/CSV — all without ever writing to, executing, or requiring network access to
the scanned source. Docker was available in this environment, so the PostgreSQL/pgvector
backend Phase 1 could only partially verify was tested against a real live instance,
including a real add()/search() vector round-trip — closing that stated gap. Two real
persistence bugs (foreign-key insert ordering) were found and fixed only because that live
database enforced constraints SQLite silently ignored.

## 2. Phase 2 objective

As stated in the task brief: discover/classify supported files, build a structured inventory,
map components to the 16 banking domains, run a limited but real set of deterministic
scanners, produce structured findings, persist scan metadata and findings, display results
through a minimal Streamlit workflow, and export a structured scan report — remaining
local-first, isolated, read-only, deterministic, and safe by default. Not in scope: the full
banking intelligence layer, RAG reasoning, control library, final scoring engine, external
agents, or final banking mockup.

## 6. Source-ingestion capabilities

`scanners/source_ingestion.py`: local directory ingestion (via the existing
`scanners/path_validator.py` allowlist) and ZIP archive ingestion. ZIP handling rejects, before
extracting anything: Zip Slip / path traversal, absolute paths (POSIX and Windows), symlink
entries, excessive entry counts, excessive total uncompressed size, and suspicious compression
ratios (zip-bomb heuristic). Extraction happens in an isolated temp directory
(`Settings.scan_temp_dir`), removed by `SourceHandle.cleanup()`. The original source (directory
or archive file) is never modified — verified by `tests/security/test_scan_no_source_modification.py`.

## 7. Supported file types

See `docs/phase2_scanning_guide.md` for the full list. Summary: Python, JS/TS(X), Java, C#,
Go, Shell, PowerShell, SQL, JSON, YAML, XML, TOML, INI/config, Markdown, plain text, CSV,
Terraform, env files, `.properties`, plus `Dockerfile`/`docker-compose.yml`/`Makefile` by
filename. No binary parsing; a null-byte sniff in `scanners/content_reader.py` is a second line
of defense even for a file that passed the extension check.

## 8. File-discovery safety limits

Per-file size (1 MB default), total scan volume (200 MB), file count (20,000), directory depth
(40), symlinks (skipped by default, never followed), archive entry count/uncompressed
size/compression ratio — all configurable via `core/config.py::Settings`, all enforced in
`scanners/file_discovery.py`/`scanners/source_ingestion.py`, all covered by dedicated unit
tests. Default-ignored directories: `.git`, `.github`, `node_modules`, `venv`, `.venv`, `env`,
`__pycache__`, `.pytest_cache`, `.mypy_cache`, `coverage`, `dist`, `build`, `target`, `bin`,
`obj`, `.idea`, `.vscode`, `.tox`, `.eggs`, `htmlcov`.

## 9. Classification capabilities

`scanners/file_classifier.py::classify_file()` deterministically assigns a `language` (for 12
programming-language extensions), a `detected_type` (dockerfile / docker_compose / terraform /
sql / ci_workflow / configuration / source_code / documentation / data_file / text), and 17
boolean category flags (programming language, configuration, IaC, deployment/environment, plus
13 domain-hint flags: database schema/migration, API definition, auth config, logging config,
monitoring config, audit-related, payment/account/credit/investment/customer-identity-related,
data-governance-related, security controls). Path/name/extension-based only — no content is
read at this stage.

## 10. Banking-domain mapping implementation

`scanners/domain_mapper.py::map_file_to_domains()` uses `core.domains.BankingDomain`
unmodified (no domain renamed, added, merged, or removed — verified by
`tests/unit/test_domain_mapper.py::test_all_sixteen_domains_remain_available`). Maps
classification flags to domains with `ConfidenceLevel.HIGH`/`MEDIUM` (15 flag→domain
mappings), plus a lower-weight `ConfidenceLevel.LOW` banking-terminology-keyword pass
(fraud/AML/sanctions, reconciliation/ledger, disaster-recovery/backup/failover,
model-governance) as a second, independent signal source. Every mapping carries `domain`,
`confidence`, `reason` (human-readable evidence), and `source`
(`models.enums.MappingSource`). A file can map to zero, one, or several domains. Unknown
content maps to zero domains — never guessed.

## 11. Implemented scanners

All 8 required categories, in `scanners/rules/`: `secret_scanner.py` (A), `pii_scanner.py`
(B), `unsafe_logging_scanner.py` (C), `audit_scanner.py` (D), `permission_scanner.py` (E),
`sql_scanner.py` (F), `insecure_config_scanner.py` (G), `unsupported_file_scanner.py` (H). Full

(`loan_approval.py::approve_loan` correctly does *not* trigger an audit-gap finding because it

## 12. Finding model

`scanners/rules/base.py::RawFinding` (in-memory, pre-persistence) and
`storage/db/models/finding.py::Finding` (persisted). Fields match the brief's list with one
deliberate exception: **the persisted table has no raw-`evidence` column, only
`masked_evidence`.** Raw evidence exists only transiently in `RawFinding`, in memory, long
enough to compute the masked version — it is never logged, displayed, or persisted. This
satisfies the brief's own "Secret values must be masked" / "Logs must be sanitized"
requirements applied to persistence as well, not only to logs and the UI. Verified structurally
(`Finding` has no `evidence` attribute) and behaviorally (a real secret scanned from the
fixture never appears in a persisted row) by `tests/unit/test_scan_repository.py`.
`finding_type` distinguishes `observed_evidence` from `inference`; `remediation_mode` is a
single-valued enum (`advisory_only`) making "never auto-fix" machine-checkable rather than
implicit.

## 13. Scan orchestration

`scanners/scan_orchestrator.py::run_scan()` implements the full flow: validate source → hash
source (before) → discover → classify → map domains → run all 7 content scanners (with
per-file try/except isolation — one unreadable/failing file does not fail the scanner or the
scan) → run the skipped-file scanner → deduplicate → hash source (after) → compare → determine
status (`completed` / `completed_with_warnings` / `failed` if integrity check fails) → return a
structured `ScanResult`. Fully synchronous, no async infrastructure, per the brief's own
"acceptable for Phase 2" allowance. `ScannerExecutionSummary` records per-scanner
processed/errored/produced counts and a sanitized error summary (never raw exception text that
could embed file content).

## 14. Persistence implementation

`storage/db/models/{scan,file_inventory,domain_mapping,finding,scanner_execution}.py`
(SQLAlchemy 2.x, `Mapped`/`mapped_column` style, consistent with Phase 1's `storage/db/base.py`),
plus `storage/db/repositories.py::ScanRepository` (explicit field-by-field mapping, no ORM
relationships/cascades — deliberately thin and inspectable). No silent fallback: `save()`
propagates any real database error rather than swallowing it; `get_engine()` raises a clear
`ConfigurationError` if `DATABASE_URL` is unset (see `docs/phase2_scanning_guide.md`'s
"PostgreSQL persistence when no server is available" section).

### 17.1 Bugs found and fixed during this implementation

- Two regex patterns (`sql_scanner.py::_STRING_CONCAT_SQL_RE`,
  `insecure_config_scanner.py`'s TLS-verification pattern) used Python's `(?i)` inline flag
  twice within one compiled pattern (once per concatenated string literal) — Python 3.11+
  rejects this (`re.error: global flags not at the start of the expression`). Found by
  importing every new module directly, fixed by keeping the inline flag only on the first
  alternative (it still applies to the whole pattern).
- `scanners/rules/permission_scanner.py`'s wildcard-Action/Resource patterns only matched
  JSON-style `"Action": "*"`, not Terraform/HCL-style `"Action" = "*"` — found while building
  the synthetic fixture's Terraform example, fixed to accept both `:` and `=`.
- Two foreign-key ordering bugs in `storage/db/repositories.py::ScanRepository.save()` — see
  §15 and §26.

## 19. Security controls

See `docs/security_boundaries.md` for the full, updated list. Summary of what's new in

## 20. Read-only integrity proof

Every scan computes a SHA-256 hash over every file in the source tree (excluding the same
ignored directories as discovery, but with no size/count limits — an integrity check, not a
scan) before and after running, and refuses to report success if they differ
(`scanners/scan_orchestrator.py`, `ScanSummary.integrity_verified`). Verified end-to-end
against the synthetic fixture and against a ZIP-sourced scan in
`tests/security/test_scan_no_source_modification.py` (2 tests) — real hashes computed via
`hashlib.sha256`, not mocked.

## 25. Known limitations

- `rag/{ingestion,chunking,retrieval,pipeline}` (document-ingestion RAG lifecycle) remains
  unbuilt — Phase 2 built source-code scanning, not document RAG. See the plan's Phase 2
  status correction note.
- `ui/streamlit_app.py` was never launched and interactively tested in a browser in this
  session — only import-verified and unit-tested at the function level.
- Scanner detection is regex/pattern-based throughout; every scanner's own finding
  `description` text says so. False positives and false negatives both exist by construction
  (e.g. `secret_scanner.py`'s env-style pattern is still line-anchored, unchanged from Phase 1;
  `audit_scanner.py`'s "no audit call nearby" check is a proximity heuristic, not control-flow
  analysis).
- `governance/pii_redaction.py`/`secret_masker.py` remain non-exhaustive (Phase 1 limitation,
  unchanged).
- No authentication anywhere (explicitly out of scope for Phase 2).
- The live-Postgres verification in §15 is a single-process, single-scan correctness check —
  not a concurrency, scale, or long-running-stability test.
- `deployment/docker-compose.yml` still defines only the `db` service — no `api`/`ui` service
  entries were added (the brief did not require them, and `app/main.py` still only has a
  `/health` route).

## 26. Remaining risks

- The foreign-key-ordering bug class found in `storage/db/repositories.py` (§17.1) suggests
  any future direct-SQLAlchemy persistence code in this codebase should be written and
  reviewed with the same "no relationship() means no automatic insert ordering" awareness —
  flagged here explicitly so Phase 3's persistence code doesn't repeat it.
- Scanner false-positive/false-negative rates have not been measured against a corpus larger
  than the one synthetic fixture — real-world noise levels are unknown.
- No performance/scale testing was done against a large real repository (only small synthetic
  fixtures and `tmp_path`-generated test trees).
